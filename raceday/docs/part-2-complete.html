Authentication is server-side

Login flow

1 · Login
Email + password
→
2 · Verify
PBKDF2 hash
→
3 · Session
UserId + Role
→
4 · Request
HttpOnly cookie

The browser receives only the opaque .RaceDay.Session cookie. The user ID and role stay in the server-side session. Every protected action gets the same treatment: no session means 401; a valid session with the wrong role means 403.

Password storage

Passwords are never stored in plain text. Each hash gets a random salt and records the PBKDF2 iteration count. Verification uses a constant-time comparison.

PBKDF2-SHA256100,000 iterationsrandom salt
Ownership is separate from role.

An Organiser can be an Organiser and still be blocked from editing someone else's event. That check happens inside the event, category, enrolment and results actions.

05

Database and seed data

Code-first alignment

RaceDayDbContext mirrors the Part 1 SQL reference: table names, column sizes, primary keys, foreign keys, unique constraints, check constraints and defaults. The SQL file remains in /docs as the approved plan.

The startup seeder creates two organisers, two participants, three events, two categories per event, sample enrolments, two results, weather snapshots and route points.

Integrity rules that matter

Unique account email
Unique category name per event
One enrolment per participant per event
One result per enrolment
Positive distance and position
Age range cannot invert
Demo credentials are for local testing only.

All seeded demo accounts use RaceDay@2026; the API hashes it on first startup. Change or remove these accounts before deployment.
